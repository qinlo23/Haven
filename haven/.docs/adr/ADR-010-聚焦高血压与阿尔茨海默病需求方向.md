# ADR-010：聚焦高血压与阿尔茨海默病需求方向

- **Status**: Accepted (2026-10-26)
- **Deciders**: Haven 项目组
- **Date**: 2026-10-26
- **Related ADRs**:
  - [ADR-001](./ADR-001-项目定位-个人慢病管理智能体.md)：延续私人健康顾问与长期陪伴定位，收敛主要病种方向。
  - [ADR-005](./ADR-005-MVP范围与项目入口.md)：保留高血压先行验证的阶段选择；本文确立后续需求方向，不表示两个病种已全部交付。
  - [ADR-006](./ADR-006-单租户身份模型.md)：沿用一个部署服务一个人的身份模型。

## Context

Haven（健健）定位为私人健康顾问。若围绕所有慢病同时开发，需求与业务规则容易持续扩散，难以集中验证具体场景的价值。

当前高血压已具备建档、血压记录、异常确认和趋势展示等基础能力；阿尔茨海默病目前仅有业务模块占位，尚未形成具体功能闭环。需要明确两者是项目主要的需求开发方向，同时区分方向决策与实际交付状态。

## Decision Drivers

- 集中有限研发资源，优先做深具体病种场景。
- 以日常记录、陪伴与信息转达为核心，保持私人健康顾问定位。
- 复用公共能力，分别维护疾病业务规则，支持同一个人存在两种疾病。
- 坚持不做医疗诊断，确定性判断与故障降级不交给 LLM 自行发挥。

## Considered Options

| 方案 | 优点 | 代价与问题 |
| --- | --- | --- |
| 面向所有慢病同时扩展 | 覆盖范围广 | 需求分散，难以形成稳定的疾病业务闭环 |
| 长期仅支持高血压 | 范围最小，可延续现有实现 | 无法承接已确定的阿尔茨海默病方向 |
| 聚焦高血压与阿尔茨海默病（采纳） | 方向明确，公共能力可复用，疾病需求可分别深化 | 需要分别梳理需求、规则与验收标准，并处理多病种共存 |

## Decision Outcome

**Haven 以高血压和阿尔茨海默病作为主要需求开发方向，优先围绕这两个病种完善私人健康顾问能力。** 文档与代码中的病名统一使用“阿尔茨海默病”。

### 需求与交付边界

- 高血压方向以现有记录、确定性校验、异常确认及趋势展示闭环为基础继续迭代。
- 阿尔茨海默病方向先明确使用场景、数据需求、安全边界和验收标准，再逐项实现；目录占位不代表已支持相关功能。
- 新需求优先判断是否直接服务这两个病种，或是否属于它们共同需要的基础能力。其他病种暂不作为主要开发方向，新增支持需另行明确范围。
- 两个方向不要求同时交付，不在本 ADR 中承诺具体功能清单或时间表；需求明细以 `requirements/` 中的后续文档为准。

### 代码与数据组织

- `application/hypertension/` 管理高血压专属业务；`application/alzheimer/` 为阿尔茨海默病业务预留位置。
- 基础档案、隐私同意、账户、命令、记忆摘要和文案入口继续作为共享能力；不为每个病种重复建立用户身份或基础档案。
- 疾病规则按模块分别实现，保持业务逻辑独立于 MDA 运行时；存储与安全能力继续由对应层负责。
- 同一个人可以同时存在两个病种。接入第二病种前，必须调整当前“保存档案时删除全部疾病记录再写入当前疾病”的行为，以及单病种校验和草稿流程，避免相互覆盖。问题已记录于 [IDEA-001](../idea/IDEA-001.md)。

### 产品与安全边界

- 继续遵守单租户、健康数据隐私及明确同意要求；增加病种不自动引入家庭协同或照护者访问权限。
- 不提供疾病诊断、处方或治疗方案，不以新增病种为由扩大模型的医学判断权限。
- 血压分级、趋势、紧急判定及未来需要的规则判断均由确定性逻辑处理；LLM 负责对话引导与结果转达。
- 工具失败、模型异常和外部依赖不可用时，保留明确降级路径，不编造结果或声称操作成功。

## Consequences

**Good:**

- 项目有明确的需求优先级，避免向泛健康助手无边界扩张。
- 高血压已有实现可以持续验证，阿尔茨海默病可按独立需求逐步推进。
- 公共能力共享、疾病业务分开，便于维护并支持多病种共存。

**Bad:**

- 其他病种需求需延后处理。
- 第二病种落地前，需要改造现有单病种建档假设，并补充对应安全规则和验收场景。

**Neutral:**

- 本次决策确立需求方向，不宣称阿尔茨海默病功能已经实现，也不改变现有运行时、部署方式和准入规则。
- 本 ADR 不改写历史决策；后续需求文档应依据本方向确定具体交付范围。
